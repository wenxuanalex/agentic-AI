## 7. Agent bugs and surprising behaviour (reported, not fixed)

1. **Ranking isn't by score.** `scoring.py:299-301` (`rank_key`, used at `batch.py:526`) sorts by the 7 criteria lexicographically, in priority order, and uses the weighted score only as the final tie-breaker. The README says candidates are ranked "by score".
   - On the real data, C02 (75.0) and C14 (73.2) outrank C04 and C11 (79.6), because their `skills_min` is 1.0 against 0.9.
   - This, together with run-to-run variation in `skills_min`, is why the shortlist changes every run.
2. **The verifier and the label readers disagree.** The verifier checks the **first** `LABEL:` line (`agent.py:245`, `labels[0]`), but `batch.py:87-90` and `run_eval.py` read the **last** one. The system prompt invites the model to "think out loud first", so if a draft `LABEL:` comes before the final one, what was verified and what was recorded can differ.
3. **Hidden text is recorded as an agent rejection.** For a disqualified CV, `batch.py:342` writes `label = "0"` even though the model never ran. In `scores.csv` this looks like the agent decided "reject".
   - `batch.py:618-629` then skips every email for these CVs, so a disqualified applicant is never told the outcome. That goes against the agent's own clause P11 ("unsuccessful candidates should be informed").
   - Any hidden character at all (`> 0`) disqualifies a CV, not the README's 20-character warning threshold (`tools.HIDDEN_FLAG_CHARS`). No real CV was affected in these runs.
4. **The parse cache leaks across repeats** (`tools.py:44-50` and `batch.py:125`). It's switched on by the first batch and never switched off. In `run_eval.py`, every later batch, parse case and repeat reuses the first parse of each file. `tools.py:41-43` says the cache is off by default "so eval repeats still measure parser variation", which isn't true once a batch has run.
5. **CV text goes to stdout.** `tools.py:233-235` prints a preview of every page's visible text ("VISIBLE DEBUG"), and `tools.py:602-606` prints the full `check_timeline` input, which is the resume text. `run_eval.py`'s parse case also prints CV text. This is a privacy risk for anyone who runs the eval in a shared terminal or CI log.
6. **The README and the code disagree on single-case emails.** `agent.py:306-318` pauses for human approval before **both** rejection and recruiter emails. The README says rejections are sent "automatically after verification succeeds".
7. **The README and the code disagree on criteria.** The README and the `scoring.py:1-23` docstring describe 6 criteria with weights 6 to 1. `CRITERIA` (`scoring.py:33-41`) has 7 criteria with weights 7 to 1, including `years_above_min`.
8. **`visible_pdf_text` fails differently from what its docstring says.** It re-raises on an unreadable file (`tools.py:246-248`), while the docstring says it returns `""`.
   - Because `parse_resume` calls it before `_check_file` (`tools.py:322-324`), a missing resume path raises an exception instead of returning `ERROR: unreadable`.
   - This is also why `test_cache_and_bad_files` fails.
9. **`check_timeline`'s experience section can end early.** It cuts the work-experience section at the first later occurrence of the word "skills", "projects" and similar words (`tools.py:576-579`). A job bullet that mentions "skills" ends the section early and undercounts experience.
   - `tools.py:447-479` is an older copy of the date helpers that is never used.
10. **The verifier's failures cluster on one pair.** 5 of the 6 eval failures are `verification_failed` on the CV_MISS × Data Scientist JD pair (22 requirements). After 2 retries no decision is made and no rejection email is sent. Rejecting a CV costs more retries than advancing one.
11. **The Data Scientist JD has no experience requirement** (`parse_jd_real` checks for this). As a result, `years_min` = 1.0 and `years_above_min` = 0.0 for every real CV, and two of the seven criteria do nothing for this JD.

**Harness issues** (in `run_eval.py`; reported, not changed beyond section 9):

- In `do_batch`, the per-JD shortlist checks after the `for jd in jd_ids:` loop (`run_eval.py:484-531`) are outdented, so they only check the last JD.
- `shortlist_per_jd` is nested under `shortlist_is_prefix_of_ranking`, so for `coverage_multi_jd` it is never evaluated.
- Neither affects the single-JD real-data results.

## 8. What changed compared with the team's last run

The previous `eval_results_baseline.csv` had 1 row (`reject_still_emailed`) because of how `run_eval.py` wrote its output:

- **Overwrite per invocation:** it collected results in memory for the whole run and wrote them once at the end, in `"w"` mode, to a fixed filename. A later `--ids reject_still_emailed` run (00:43, after the full suite's last batch at 00:32) overwrote the full-suite file.
- **Score copies could collide:** the copies were named with a per-invocation counter (`scores_<folder>_base_r1_<n>.csv`), so they could overwrite each other between runs too.
- **Crashes lost everything:** a crash before the end lost every row.
